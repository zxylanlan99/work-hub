## 问题一：PRD 未显式说明"应保留的 V1.x 基础功能"

### 1.1 缺口确认（结论：确实存在缺口）

**事实判定**：PRD 当前**确实缺失"基础功能保留清单"**。

证据链：
1. **PRD 附录 A（V1.x 现状要点）** 仅描述 V1.x 现状（前端原生 JS、后端 FastAPI、CloudBase 集合、设置多厂商模型等），性质标注为"理解背景，非需求"。它**没有**列出哪些功能必须保留。
2. **PRD 正文以新功能/增强为主**（§3 用户故事、§4 需求池、§6 详细规格），仅在零散的验收标准里出现"复用 V1.x"：
   - `V2-PLAN-001 AC2` 复用 `goals/milestones/tasks` + `confirmCreateGoalFromPlan`
   - `V2-AGENT-001 AC2` 记忆按 `agent_id` 隔离"与 V1.x `agent_memory` 一致"
   - `V2-REVIEW-001 AC1` 关联 `review_cards`
   - `V2-KB-001 AC3` 保留"资讯可入库知识库"链路
   - `V2-SET-002 AC3` 复用 `settings.html` 逻辑
   - `V2-ARCH-001` "保留 V1.x 模块边界与 CloudBase 集合"
3. 这些"复用"表述**分散、非系统、非承诺式**——工程师在全量重写前端（架构 §2.1 明确"不保留 V1.x 文件"）时，容易误判哪些"基础盘"是**必须平移**而非可丢弃，从而在新代码里漏掉分类管理、收藏、首页统计等"无独立需求编号"的基础功能。

**结论**：PRD 缺少一份"V2.0 基础功能保留清单（非变更项）"，属于明确缺口，需回填。

## 问题二：AI 底座架构是否兼容 FastGPT 的智能体管理？能否直接用 FastGPT 智能体替代 Agno？

### 2.1 事实澄清

- **FastGPT 平台本身具备智能体（Agent）管理能力**：其"应用"体系包含 AI 对话应用、**Agent 应用**（可挂工作流/插件/工具）、**技能（插件/HTTP 工具/MCP）**、**知识库引用**、**多轮对话记忆（Session）**等。即 FastGPT 既能当 RAG 后端，也能当 Agent 编排平台。
- **当前架构只把 FastGPT 当 RAG 引擎**：架构 §2.3、§3.4 明确 FastGPT 仅负责"解析/切片/向量化/检索/重排"，经 `kb-service(:8004)` 网关封装为 `/api/kb/*`；**未启用 FastGPT 的 Agent 应用/技能模块**。智能体大脑由 `Agno`（agent-service :8001）独立实现。

### 2.2 兼容性分析（双记忆 / 双编排风险）

当前"Agno 大脑 + FastGPT 仅检索"架构，与"同时启用 FastGPT Agent 模块"在**技术上是并存相容但语义冲突**：

- **两边都有 Session / Memory / Tool 抽象**：Agno 有 `agent_id` 级 Session+Memory、自有 Tool（web_search/knowledge_base/code_exec）；FastGPT Agent 有"应用+对话"级记忆、自有插件/工具体系。**若同时启用，系统将出现两套并行编排与两套记忆。**
- 具体冲突：
  1. **双记忆不一致**：同一用户的"规划师"对话，Agno 存一份（agent_id 隔离），FastGPT 若也承接 Agent 对话则存另一份。跨会话/跨智能体引用错乱，且无法保证"规划师看不到写作闲聊"的隔离语义。
  2. **引用归属混乱**：Agno 的 citations 来自 `kb-service` 检索切片（与 LLM 解耦，见架构 §3.1）；FastGPT Agent 的引用来自 FastGPT 内部知识库（与 Agent 输出耦合）。前端将面对两套 citation 来源，无法统一展示与溯源。
  3. **密钥/编排分散**：架构 §2.5/§7/§10 明令"密钥仅 agent-service 调厂商"。若启用 FastGPT Agent，FastGPT 需自带模型接入（OneAPI 等），密钥从 agent-service 分流到 FastGPT，违背集中密钥基线，暴露面扩大。
  4. **工具/Skill 分裂**：自定义 Skill（V2-AGENT-003）在 Agno 侧落库为 `agent_skills`、运行时装配为 Tool；FastGPT Agent 则用平台 plugin 体系。同一"用户自定义 Skill"无法两侧复用，维护成本翻倍。
- **结论**：两者"能并存部署"（FastGPT 同时跑 RAG + Agent 不会崩溃），但**不应同时承担智能体编排职责**——否则在记忆、引用、密钥、Skill 四个维度产生不可接受的分裂。

### 2.3 权衡对照表：能否直接用 FastGPT 智能体替代 Agno？

| 维度 | Agno（当前选型，agent-service 大脑） | FastGPT Agent 应用（替代方案） | 评判 |
|------|--------------------------------------|-------------------------------|------|
| 解耦性 / 去平台绑定 | **高**：纯 Python 底座（MIT），不绑平台，可独立替换 | **低**：绑死 FastGPT，退出成本极高（智能体+知识库全绑） | Agno 胜 |
| 前端"智能体中心"体验契合度 | **高**：前端直连 agent-service，对话/引用/Skill 库完全自控 | **中低**：需套 FastGPT 应用界面或 API，体验受平台约束 | Agno 胜 |
| 用户自定义智能体 + 自定义 Skill 运行时装配 | **高**：运行时 prompt + 工具白名单建 Agent，落库 `agent_skills` | **中**：FastGPT 应用配置较重，自定义 Skill 需平台 plugin，灵活度低 | Agno 胜 |
| 记忆隔离粒度 | **精确**：`agent_id` 维度，严格契合"规划师看不到写作闲聊" | **弱**：按"应用+会话"隔离，语义不同，难保证 agent_id 级隔离 | Agno 胜 |
| code_exec 沙箱可控性 | **高**：自管 Docker/nsjail 沙箱，触网策略可控（架构 §2.2） | **低**：依赖 FastGPT 沙箱/插件，可控性弱 | Agno 胜 |
| 密钥集中（仅 agent-service 调厂商） | **高**：唯一 LLM 调用方（架构 §2.5） | **低**：FastGPT 需自带模型接入，密钥分散 | Agno 胜 |
| 引用 / citation 解耦 | **高**：引用来自 kb-service 检索切片，与 LLM 解耦 | **低**：引用来自 FastGPT 内部，与 Agent 输出耦合，且与我方体系冲突 | Agno 胜 |
| 演进 V1.x 5 智能体 + 记忆逻辑 | **直接平移**：Instruction+Tool+Session/Memory | **重写**：需转为 FastGPT 应用配置 | Agno 胜 |
| 运维成本 | 低（轻量 pip，~无额外资源） | 低（已部署）但增加编排复杂度 | 持平 |
| 并发 / 社区版限制 | 无限制（自托管） | 社区版有并发/应用数限制，或影响智能体并发 | Agno 胜 |

**结论：不能直接用 FastGPT 智能体替代 Agno。** 当前"Agno 做大脑 + FastGPT 仅作知识库检索后端"的取舍**成立（有条件成立）**。

### 2.4 架构决策建议：是否需补强约束？§2.3 是否足够？

- **当前 §2.3 不足**：§2.3 只写了 FastGPT"负责解析/切片/向量化/检索/重排""不自己维护向量与切片"，并说"职责切分"。它**未显式声明禁用 FastGPT Agent 应用模块**。约束是隐含的（从"仅 kb-service 封装 /api/kb/*"可推断），但**缺少一条硬禁令**，容易被后续工程师误启用 FastGPT 的 Agent/应用能力。
- **建议补强一条显式约束**（写入架构 §2.3 末尾 + §7 约束区）：
  > **C3 · 禁用 FastGPT Agent 应用模块**：FastGPT 仅用作无状态知识库检索后端（经 kb-service `/api/kb/*`），**不得启用其 Agent 应用 / 技能(插件) / 多轮记忆编排**；所有智能体编排、记忆、工具、密钥统一收敛于 agent-service(Agno)，避免双记忆/双编排/密钥分散。

### 2.5 风险清单（若误用 FastGPT Agent 模块会怎样）

| 风险 | 触发 | 后果 |
|------|------|------|
| R-1 双记忆不一致 | Agno 与 FastGPT 同时存对话 | 跨会话/跨智能体引用错乱，记忆不可信 |
| R-2 引用归属混乱 | 两套 citation 体系并存 | 前端无法统一展示，溯源 debug 困难 |
| R-3 密钥分散 | FastGPT 自带模型接入 | 违背"密钥仅 agent-service"，暴露面扩大 |
| R-4 工具/Skill 分裂 | 两套 Tool 抽象 | 自定义 Skill 无法复用，维护翻倍 |
| R-5 记忆隔离粒度不符 | FastGPT 按应用+会话隔离 | 无法保证 agent_id 级隔离，破坏隐私基线 |
| R-6 平台绑定加深 | 智能体+知识库都绑 FastGPT | 违背"可插拔知识库"，退出成本剧增 |
| R-7 社区版限制 | 并发/应用数受限 | 智能体并发体验受损 |
| R-8 可观测性下降 | 编排分散 | `trace_id`/`agent_id` 链路断裂，日志难统一 |

### 2.6 最终评价结论（一句话）

> **当前"Agno 做大脑 + FastGPT 仅作无状态知识库检索后端"的取舍成立且应当被显式固化（补 C3 硬约束）；不应启用 FastGPT 的 Agent/应用模块，否则将引入双记忆、双编排、密钥分散三重风险，直接破坏 V2.0 的解耦基线与记忆隔离承诺。**
